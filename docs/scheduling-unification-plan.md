# 系统定时任务统一管理方案

状态：已按确认方案实施并完成验证。下方任务清单记录改造前的行为。

## 改造前任务清单

| 任务 | 当前触发方式 | 配置与状态 | 执行记录 |
| --- | --- | --- | --- |
| 订阅增量抓取 | 五段 cron + IANA 时区；旧订阅兼容分钟周期 | `subscriptions` 记录，输出库与订阅页面；需启用并完成初始化，已有列表任务时等待 | `jobs` / 子任务 / 日志 |
| 外部整理库同步位置 | 默认每 10 分钟，启动后首轮调度也执行 | `external_sync_interval`，设置页面；运行或暂停中的同步任务存在时不重复排队，待处理库变更跳过 | `locate` 任务 |
| 播放连通性检测 | 默认每 60 分钟，启动后等待一个周期；手动检测重置周期起点 | `health_interval`，设置页面；内存中保存检测任务和上次启动时间 | 连通性状态与播放日志，无统一任务记录 |
| 来源库 / 排除库归并 | 任务完成等事件触发；每 10 分钟兜底 | 代码常量 `SETTLE_INTERVAL`，内存标记与时间 | 日志，无独立执行历史 |
| 外部整理库回收区到期清理 | 启动后首轮维护，之后每小时检查 | 代码常量 `HOUSEKEEP_INTERVAL`；`trash_days` 决定保留天数，不是执行周期 | 日志 |
| 播放记录到期 / 超量清理 | 与回收区清理共用每小时维护 | 保留天数和最大条数可设置，执行周期不可设置 | 无统一执行历史 |
| 外部整理库残留清理 | 每小时维护时检查，距最近一次应用型清理任务满 24 小时后排队 | `orphan_cleanup` 开关，代码常量 `TIDY_INTERVAL`；已有运行 / 暂停任务时不重复排队 | `tidy` 任务 |

实际任务发现集中在 `hls2strm/engine.py` 的 `_schedule_loop()` / `_housekeep()`；订阅时间计算在 `hls2strm/subscription_schedule.py`。

还有运行基础设施：每约 30 秒检查调度并保存有变更的连通性状态；启动时统计缺失文件；任务日志在执行期间约每秒批量落库。它们可在页面的系统运行信息中说明，无需提供 cron 编辑。

缓存 TTL、重试退避、源站冷却、播放链接有效期、保留天数是执行策略或失效条件，不属于独立的定时任务。

## 目前的问题

1. 计划分散在订阅记录、全局设置和代码常量中，不能在一个页面查看和调整。
2. 部分周期起点只在内存中，重启后的行为取决于各自代码，用户看不到原因。
3. 只有订阅显示较完整的下次执行时间；系统维护缺少统一的上次结果、下次时间和跳过原因。
4. 执行有的进入任务队列，有的直接在调度循环执行，记录方式不同。
5. “全局暂停”会暂停订阅、位置同步、连通性检测、归并以及新残留清理任务；回收区到期清理与播放记录清理仍执行。
6. 每小时维护把三个任务绑在一起，修改其中一个频率会影响其他任务；维护或归并执行时间较长，也会推迟后续调度检查。

## 推荐的统一范围

统一计划模型、时间计算、调度入口、执行状态和管理页面，同时保留 cron 与固定间隔两种时间语义。

- 固定间隔：每 N 分钟，例如位置同步、连通性检测。
- Cron：在指定时区的固定时间点执行，例如每天 03:15 的抓取或清理。
- 仅手动 / 停用：分别表示没有自动计划以及计划存在但暂不启用。
- 归并另外保留事件触发，定时配置只管理兜底检查；事件触发不改成等待 cron。

不能把所有间隔自动改成 cron：`*/10 * * * *` 是每小时的 00、10、20 等分钟触发，不是从上次执行起每隔 10 分钟；90 分钟等周期也无法通过一个简单的五段 cron 无损表达。现有分钟周期默认原样保留，用户主动切换时预览新的时间安排。

## 统一页面

侧栏新增“定时任务”，与现有“任务”页面相邻。

表格列：名称、任务类别、作用对象、计划（中文摘要 / 原始表达式 / 时区）、启用状态、当前状态、上次开始、上次结果、下次计划时间、操作。

状态应区分：待调度、已排队、执行中、未完成首轮全量、站点停用、全局暂停、库变更未完成、已有任务、无适用对象、失败。下次计划时间与实际开始时间分别显示，不能把正在排队的任务表示为已经执行。

支持按系统任务 / 订阅、启用状态和执行状态筛选，搜索名称和关联库。

操作：启用 / 停用、编辑计划、立即执行、查看执行历史、跳转关联的任务 / 订阅 / 输出库。查看页面、预览时间和保存计划不会触发抓取、文件清理或执行任务；“立即执行”复用现有业务检查，不能绕过排除库等待和库变更保护。涉及删除文件的立即清理需要沿用相应确认流程。

计划编辑共用组件：固定间隔、常用时间快捷选项和自定义 cron；时区默认 `Asia/Shanghai`；显示接下来几次计划时间以及启动后 / 停机漏执行的策略。

现有输出库与订阅页仍负责库和订阅的业务配置；其计划编辑与新页面共用组件和 API。设置页保留保留天数、抽样数量等业务参数，把计划频率入口改为指向“定时任务”，避免两份独立配置。

## 实现结构

1. 将订阅专用时间计算提取为共用调度模块，统一 cron / 固定间隔校验、时间预览和到期判断。
2. 建立固定的系统任务注册列表，注册同步位置、连通性检测、归并兜底、回收区清理、播放记录清理、残留清理；注册列表决定每类任务允许的操作和执行条件。
3. 订阅计划继续以现有订阅记录为唯一来源；系统计划集中持久化。用统一的计划标识（如 `subscription:123`、`system:external_locate`）聚合到同一查询和管理 API，避免复制订阅计划导致两边不同步。
4. 持久化系统计划及必要的运行状态，建立统一执行记录，保存计划标识、触发来源、计划时间、开始 / 完成时间、结果、错误摘要和关联 `job_id`。读取旧日志不能伪造历史执行记录。
5. 调度循环只负责到期判断和发起执行，扫描与清理从循环中分离。已有业务队列任务继续复用；直接执行的系统维护使用受管后台任务，并记录结果、避免同类并发、在停机时收尾。
6. 拆分每小时维护的三个动作，各自拥有计划和状态。保留原默认频率与条件，统一管理不顺带扩大删除范围。

暂不引入外部调度服务或分布式执行组件，复用现有 `croniter`、SQLite 和任务队列。

## 兼容与执行策略

- 保留订阅 ID、初始化状态、历史进度、来源 / 排除关系、任务历史和导入导出兼容；排除库等待条件仍依据真实启用的订阅计划及完成记录计算。
- 从现有设置导入系统计划默认值。数据库迁移只初始化缺失的计划，重启不覆盖用户已修改的计划。
- 订阅保留重启不补跑停机期间 cron、运行期间延迟最多补一次的行为，不补跑一串历史任务。
- 位置同步保留启动后执行一次；连通性检测保留启动后等待一个周期；清理保留现有启动和保留策略。页面明确展示差异。
- 同类任务运行中不重复排队。手动执行对周期起点的影响要有明确规则，并由前后端共用同一时间计算。
- 首阶段保留现有业务暂停与系统维护的暂停边界，在页面标明“系统维护不随业务暂停”；不默默改变已有全局暂停的范围。
- 归并事件触发属于库一致性流程，不能因停用定时兜底而关闭；首次迁移保留现有排除库和文件变更互斥保护。
- 同步位置仍只找回已有文件；目录离线不补文件。清理仍保留目录归属、文件类型、改动时间和回收区天数的检查。

## 实施与验证

- SQLite v21 新增 `system_schedules` 和 `schedule_runs`，默认计划从旧设置初始化，重启不会覆盖已编辑计划；订阅计划仍保存在原订阅记录中。
- `schedule.py` 提供共用计划校验和预览；`scheduler.py` 统一调度；`schedule_store.py` 管理计划与运行记录；`schedule_api.py` 提供已鉴权的统一管理接口。
- 系统扫描 / 清理通过已有任务队列或受管后台任务执行，不阻塞调度循环。回收区清理停止时会等已经开始的目录处理收尾，再释放文件变更保护。
- 侧栏新增“定时任务”；订阅表单共用计划编辑器，保留旧分钟间隔。原位置同步、残留清理、订阅运行入口也关联到统一历史。
- 清理的立即执行须确认；同一提交标识复用回执，运行中不会重复提交。查看、时间预览、计划编辑不执行业务动作。
- 验证：完整后端测试 `247 passed, 2 skipped`；前端 `npm run build` 通过；真实 Edge 浏览器验证桌面 1440×1000 和手机 390×844，涵盖非法 cron 阻止保存、时间预览、90 分钟计划保存 / 刷新、启用、筛选、清理确认、执行结果、订阅配置跳转、手机横向表格和编辑弹窗，无页面脚本错误。
- 仅在临时 SQLite、临时文件目录及本地浏览器验证，没有升级生产数据库或部署线上服务。

兼容入口：旧设置 API 的 `external_sync_interval`、`health_interval` 和 `orphan_cleanup` 仍可接受旧客户端提交，写入时同步到系统计划；实际调度以系统计划表为准。新的界面不再独立编辑这些旧设置。现有库 / 订阅导入导出格式保持原范围，不包含系统计划；完整数据库备份包含系统计划及历史。
